# 实现经验：实际问题、解决思路与 Mac 避坑方式

本文件按问题组织，不把聊天过程当作技术规范。标为“已修复/已实测”的结论只适用于列出的范围；Mac 建议需要在本机复验。对应代码均在仓库 `scripts/`、`app/`、`tests/`，文件职责见[文档导航](DOCUMENT_MAP.md)。

## 1. 安装探针把 Codex 预装当成隐藏前提

**问题：** 原 CLI 的 preflight 同时检查 Linux 工具和已经安装的 Codex，新容器尚未安装时直接停止，形成“必须先装才能准备”的循环。

**处理：** 拆出 `preflightRemoteBase`，先验证 SSH、home、架构、基础库和 Linux 工具；在 Server 与配置准备之后，再检查 Codex 注册包、版本与调用链。

**Mac 应用：** 第一个认证探针必须能连接没有 Server/Codex 的干净 Linux；不要把已装好 Codex 的旧容器当作首次安装通过。客户端 macOS 检查也与远端 Linux 检查分开。

## 2. 下载成功来自不同主体

**问题：** 本机 curl 联网成功，不能说明 Remote SSH 能下载 Server，也不能说明远端扩展宿主或 Codex 后端能联网。为每个环节再造下载器会迅速扩大范围。

**处理：** Server 使用 Remote SSH 官方准备路径并核对运行结果；Codex 由用户从目标远端窗口的商店安装。按用户决策删除插件元数据/VSIX 下载、暂存和安装回退；保留维护者准备并校验随包 Node 的能力。

**Mac 应用：** 不恢复已经移出范围的插件下载功能。记录下载主体与实际失败步骤；不要用关 TLS、代理全局环境或改扩展自动更新掩盖问题。

## 3. 网页确认与 SSH 密码争用 stdin

**问题：** 网页后端如果再开 readline 读取输入，或由无 TTY 后台启动，可能吞掉认证、让密码无处输入，造成“点击了没有显示”。

**处理：** Node 留在原生终端，SSH 的 stdin/stderr 继承终端，stdout 仅做受限协议解析；网页选择通过 HTTP resolve 对应等待，不读取终端密码。缺 TTY 提前停止并明确提示。

**Mac 应用：** Finder 入口、Terminal 中启动、CLI 与 browser wait 都要实际验证。不要认为 macOS 上 `stdio:inherit` 就必然具备预期控制终端；SSH 可能访问控制终端，密码提示也不属于可随意捕获的普通日志。

## 4. 操作者漏掉认证提示造成假故障

**实际观察：** 维护者自动化循环丢弃最后一次工具输出，漏掉原生密码提示，最终远端端口检查超时。重新及时认证后同包五层全部通过。

**处理：** 保存每轮最后输出，下一轮先处理尚未回答的明确提示；只向已核对目标的原生提示输入。没有把这次操作编排错误改造成产品绕过认证。

**Mac 应用：** 不盲目按间隔投递密码，不把密码放参数、环境、临时脚本或网页字段。产品等待、操作者控制和 SSH 本身要分层诊断。

## 5. 端口监听被检查连接自己创建

**问题：** verify 如果继承 SSH config 的 RemoteForward，连接一建好就创建被检查端口，会把一个临时检查隧道误认为 VS Code 正式会话可用。

**处理：** 检查/文件传输使用隔离参数，清除转发、禁用复用；正式转发由目标 VS Code 会话承担。校验监听位置、目标端口、IPv4 回环和未知占用。

**Mac 应用：** 用实际 macOS OpenSSH 版本测试有效参数与 `ssh -G`，不能只看命令字符串。先证明没有正式 VS Code 连接时探针不会自己造出端口，再验证连接后的真实监听。

## 6. 移除代理误删 SSH 连接

**问题：** 把连接块和转发当成一个事务，remove 就可能删掉用户以后仍要使用的 alias。旧容器不可达时，一条活动恢复记录也会阻塞新容器。

**处理：** connection 与 forwarding/settings 分资源归属；remove 只撤代理，abandon 再单独决定是否清理工具连接。真实 Windows 测试已证明移除后仍能新认证。

**Mac 应用：** 直接继承这个领域模型，不重新合成一个“SSH 配置完成”布尔值。Mac 验收必须包括移除后普通 SSH，而不只检查文件里 Host 还在。

## 7. 等价配置被“接管”或空预览

**实际问题：** 测试目标已经有两个等价代理字段。最初页面预览为空且仍要求多余重连；如果把等价复用登记成工具修改，移除会损坏用户配置。

**处理：** 明确显示两个字段、等价复用、不改写及无删除所有权；`reused/owned=false`。只有本次确实改变转发或 settings 才增加这次必要重连。原样摘要在移除后仍一致。

**Mac 应用：** 同时验证缺失文件、等价已有值、冲突已有值、用户后续修改四类。等价样本不能充当真实首次写入或实际恢复的证据。

## 8. 整体重写 JSONC 和未知配置布局

**问题：** 整体 parse/stringify 会丢注释、改变顺序或换行。曾发现单行 JSONC 插入重排无关字段。通用 SSH Include/Match 解析又会显著扩大范围。

**处理：** `jsonc-parser` 局部修改、精确摘要和最小逆操作；支持范围只覆盖能安全核对的唯一字面 Host 块。拒绝重复目标、未知标记、链接文件和不支持布局。

**Mac 应用：** 保留 BOM、CRLF/LF 和无关字段的测试。Mac 常见 dotfiles symlink 仍需明确支持决策，不能为求“跑通”删除保护或自动覆盖用户符号链接。

## 9. 只有退出码，没有远端写入是否结束的证明

**问题：** SSH 断开、客户端被取消、回执丢失都不等于远端写者已经结束。边写边恢复会让迟到写者覆盖恢复结果。

**处理：** 先持久化 pendingWrite 和唯一身份，再建立受限暂存、提交许可和 guard；远端核对请求摘要与 before/after。许可关闭、guard 异常、第三种内容和回执丢失分别处理，不能用 phase 推断成功。异常退出不会无条件释放 guard。

**Mac 应用：** 远端仍是 Linux，协议可复用，传输与取消适配仍需真实试验。先在专用私有合成目录测试，再进入真实 settings；不要在 Mac 本地执行 Linux 的 `stat -c`、`sync -f` 等协议命令。

## 10. 已取消的 signal 让恢复立即失败

**问题：** 所有分支共享同一个 AbortSignal，用户取消后恢复也立即被取消，页面却可能过早说“已取消”。

**处理：** 先停止推进并核对原任务，之后独立且有界地收尾。取消结果必须在真实子进程 close 和状态收敛后报告；不能确认则保留 unknown 与定位信息。

**Mac 应用：** 分别测试按钮取消、真实 Ctrl+C、终端关闭、进程异常结束以及 SCP 中断；不是所有动作在 macOS 下都产生相同信号。

## 11. 遗留锁按 PID 或时间自动删除

**问题：** PID 会复用，锁也可能属于仍在执行的传输；“超时很久”不构成接管证明。

**处理：** Windows 恢复入口有独立系统 Mutex、进程启动身份、SSH/SCP 普查、状态来源前后复核及明确 RECOVER；只接管已核对的工具锁，不重放配置。旧远端 unknown 缺写者结束证据仍保持保护。

**代价：** 当前普查系统全部 SSH/SCP，会被其他正常远程窗口保守阻塞。曾多次要求关闭目标窗口才继续；这不是一个已经优化好的 Mac 方案。

**Mac 应用：** 重新选择崩溃后可释放的恢复互斥和可靠启动身份来源，验证多个恢复者、PID 复用、恢复者自己崩溃。不能把非 Windows 分支的 `Date.now()-process.uptime()` 当作与 OS 精确进程启动身份完全等价。不要全盘 kill SSH 或让用户手删锁。

## 12. 内核整数精度与文件替换竞态

**实际问题：** Windows inode 可超出 JavaScript 安全整数，清理时会误判归属；暂存目录碰撞和并发创建 `.ssh` 也可能误清别人的目录或改其权限。

**处理：** bigint 读取，十进制字符串持久化、精确比较；独占创建、持有文件句柄再复核身份，仅清理明确归属的对象。发现另一个创建者则重新读取，不接管其 ACL。

**Mac 应用：** inode/dev/PID 启动标识沿用精确表示；验证 APFS、普通用户、已有目录权限、原子替换和文件 mode。首次创建工具目录与接管已有用户目录是不同动作。

## 13. 扩展目录不等于有效安装

**实际问题：** `openai.chatgpt-*` glob 同时看到当前包和卸载残留目录，错误报告多个版本。目录最新或名字最大也不一定是正在加载的包。

**处理：** 读取标准 `extensions.json`，唯一选择有效注册项，校验 ID、version、平台、relativeLocation 与标准 file path；以注册摘要贯穿静态调用链及进程检查，过程中变化就停止。缺失、损坏、重复和错误平台分别有回归。

**Mac 应用：** Mac 是客户端，扩展后端运行在哪一侧必须实际确认。远端 Linux x64/arm64 不由 Mac CPU 决定。不要为通过静态检查强行降级用户扩展、删残留目录或关闭自动更新。

## 14. 看到 Codex 进程就认为 UI 正常

**实际问题：** 用户看到 `Codex could not start`。日志为 renderer_ready_timeout，30 秒内没收到 webview ready；后端已运行，代理字段匹配，七个入口引用资源也存在。

**处理：** 分开检查 UI、扩展宿主、后端和网络。通过正常重载、重新认证恢复 UI，后续关闭目标窗口再重连也正常；没有重装/降级。最初超时的唯一底层原因仍未知。

**Mac 应用：** 不把 bubblewrap 的可回退警告或同时间网络日志直接定为 UI 根因。先取与症状对应的日志和可重复信号，再逐个变量检验。Mac 上也不能用 CLI 正常替代 VS Code webview 正常。

## 15. 新回复、401 与路径归因混成一个成功

**问题：** 自动探测拿到 HTTPS 401 表示无凭证访问到目标；旧聊天里已有一条“ok”也不能证明这次请求。同时段代理日志可能来自其他进程。

**处理：** 五层、新回复、目标 PID/socket 分开。真实官方界面提交唯一标记请求，确认本次回复；自动网络探测结束后才建立观察基线，匹配该 PID 拥有的新 socket inode 与代理端口。

**Mac 应用：** 可以复用 Linux 采集思路，但必须针对此次运行后端身份；已有长连接不升级成新连接证据。没有新连接时写 unknown，不用新回复倒推流量一定经过代理。

## 16. 采样次数乘间隔不是实际观察时长

**实际问题：** 60 秒采集按 240 次 × 250 ms 推算，忽略读取 `/proc`、启动命令等耗时，最终超出 SSH 75 秒预算。

**处理：** 用实际时间截止并保留最大采样上限，回执接受实际次数并验证首次观察不超界。修复后 30 秒窗口取得 64 次采样，新增代理连接及同窗口新回复均取得。

**Mac 应用：** 远端工作耗时、认证等待和传输等待分开测量；截止算法需考虑系统时钟调整和传输超时，不用未测量的进度百分比或理论秒数充当实测。当前有上限的实现不是实时采样保证。

## 17. 自动化控制字符冒充物理 Ctrl+C

**实际观察：** 向 ConPTY 写 0x03 后 SSH 退出，但 Node 仍在，页面最终失败；正常退出页面才释放 Node 与实例锁。

**处理：** 保留 physicalCtrlCVerified=false，没有把这项标为物理 Ctrl+C 通过。自然会话中断与受控强关也分开登记。

**Mac 应用：** 原生 Terminal 下真实按键、关闭窗口、SIGINT/SIGTERM 与强制结束分别采证。脚本 emit 信号只算单元/受控测试，不能替代终端生命周期验收。

## 18. 本地网页也需要请求边界

**问题：** 只绑定 localhost 不能防其他网页尝试跨站请求；刷新和重复点击也会造成重复操作。

**处理：** 回环监听、随机临时会话、Host/Origin/请求头校验、固定静态资源、受限 JSON、CSP、去重、busy 和只读状态投影。页面不返回配置正文、完整恢复逆操作或原始 SSH 错误。

**Mac 应用：** 复用 HTTP 安全语义，不为了“本机方便”去掉限制；浏览器启动只接收程序自己生成的 URL。换浏览器、刷新、旧 token、重复提交都要复验。

## 19. 包从开发环境能启动不等于用户包可用

**实际问题：** 启动依赖开发机 PATH、Node、工作目录、字符转义或未打入包的依赖时，会在用户机器失败。特殊字符路径也会暴露 shell 拼接问题。

**处理：** 固定官方 Node 及摘要、依赖锁和许可证，生产文件白名单、逐文件 manifest、外部 ZIP 摘要；解压后空 PATH、中文/空格/特殊字符、损坏和无 TTY 拒绝有检查。源码新增维护脚本不必进入产品包。

**Mac 应用：** 必须新做 darwin/架构对应运行时、执行位、解压、Finder 启动和下载来源的门禁验证。不要把 node.exe 换名当 Mac 运行时，也不要在签名/公证/隔离问题出现时默认教用户全局关闭保护。

## 20. 文档、代码、证据各有不同时间

**问题：** PRD 开头设计时“尚未实现”、旧 README 已交付 v0.1、最新 Spec 部分实测可能同时存在。Git commit 也可能早于未提交的新代码。

**处理：** 使用明确版本导航和最新验证补记；保留失败历史，不用后来通过覆盖最初失败。本次把当前实现及交接文档分别提交并推送，Mac 获取最新 main 后可同时核对文档、源码与提交记录，而非只拿一个旧 Git SHA。

**Mac 应用：** 新建 Mac 需求增量与验证记录，复用契约但不照抄 Windows 支持声明。重新运行测试并登记 skip，不能因 Windows 专项在 Mac 跳过、总数变少就报同等通过。

## 21. 偶发测试失败不应凭猜测改产品

**实际观察：** 一次旧版 remove 用例的配置准备断言失败，原始诊断不足；单跑通过，增加失败诊断后全量通过。没有找到唯一原因，因此没有据此修改生产恢复逻辑。

**处理：** 保留第一次失败、补有用且脱敏的断言信息、单跑和全量复验，区分已修复与未定位。另有并行启动测试超时调整，仍核对真实子进程结束，不只放宽断言。

**Mac 应用：** 平台差异造成的超时、路径与权限问题要先有红色反馈，再改最小边界；不要为了绿灯跳过关键状态或恢复检查。

## 22. 频繁中断导致用户疲劳

**观察：** 按技术细节每步都请用户输入“完成”，真实验证会很慢，也容易丢失状态。用户希望尽量由助手完成操作。

**处理方向：** 先自动完成授权范围内的实现、自查和可逆准备；需要产品预览时以具体变更呈现，官方登录和不可替代确认集中安排。记录目标/周期/包/当前问题，重启时从事实继续，避免重新初始化。

**Mac 应用：** 在具备工具与明确授权时可由操作者代点已审核的产品确认；仍区分操作者行为与产品功能，不把“一次获准代输密码”实现为通用密码桥。用户批准的是具体目标和操作，不能当成永久跨机器授权。

## 接手后的检查习惯

每个可验证代码单元按“对应契约 → 最小 diff → 相关测试 → 共享逻辑全量回归 → 真实证据边界 → 记录限制”闭环推进。问题已解决且验证足够时停止扩展；未知项保留未知，不为凑全绿做隐式接管、全局代理或关闭安全机制。
