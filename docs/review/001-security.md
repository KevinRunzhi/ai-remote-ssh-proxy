评审对象：`docs/adr/0001`–`0021`、`CONTEXT.md`。每个问题给出：现状、风险、理由、建议，以及**第 2 轮复查状态**（已解决 / 部分解决 / 未处理）。

状态标记说明：

- ✅ **已解决**：有 ADR 明确覆盖该问题，且方案合理；
- 🟡 **部分解决**：主体已覆盖，但明确存在剩余缺口；
- ❌ **未处理**：相关文档无变化或新增内容未触及。

## 问题 1：远程 loopback 绑定无法阻止同主机其他用户/进程访问（高）❌ 未处理

**相关文档**：[ADR-0007](../adr/0007-bind-the-remote-proxy-to-ipv4-loopback-only.md)

**现状**：ADR-0007 规定所有 Remote Proxy Endpoint 显式绑定 `127.0.0.1`，理由是避免 wildcard 或远程网络地址让 Local Proxy 被其他用户或主机通过 GatewayPorts 访问。ADR 明确把"与容器、其他服务器用户、邻居机器共享转发端口"排除在首发安全边界之外。

**风险**：`127.0.0.1:port` 只挡住**网络上的其他主机**，不挡住**同一台远程主机上的其他本地用户和进程**。任何能在该主机上执行代码的用户都可以直接连接这个端口，进而使用用户本地计算机上的代理。也就是说：

- 共享开发机（企业内部常见：一台大机器多人登录）上，其他用户的任意进程都能白嫖或滥用这个代理；
- 远程主机上任何被入侵的低权限进程（包括恶意 npm 包、被劫持的构建脚本）都自动获得"经由受害者本地代理出网"的能力——这是一个现成的隐蔽外传通道（data exfiltration channel）；
- 该访问**完全不需要任何凭据**（配合 ADR-0005 只支持无认证代理）。

**理由**：ADR-0007 写得很清楚作者考虑过"other users"，但把它当作"out of scope"处理，而不是当作威胁写进威胁模型。问题在于目标用户（用 VS Code Remote SSH 的开发者）恰恰有相当比例在使用共享服务器。如果产品不做任何检测或告警就开洞，"scope 外"不等于"不会发生"。安全设计的惯例是：接受的风险要**显式声明并尽告知义务**，而不是靠范围划走。

**建议**（三选一，按工程成本递增）：

1. **最低限度**：在 `SECURITY.md` 和产品文档中显式声明此威胁模型："远程主机上的任何本地进程均可访问转发端口，请勿在不受信的多用户主机上使用"。并在 `doctor` / `configure` 输出中提示。
2. **中等**：优先使用 SSH 的 Unix domain socket 转发（`RemoteForward` 支持 socket 路径），socket 放在 `~/.ssh/` 下并 `chmod 0600`，配合文件系统权限天然隔离其他用户；对只支持 HTTP 代理且需要 TCP 端口的工具再回退到 TCP + 告警。
3. **彻底**（可延后）：评估 per-user loopback 地址段，但 Linux 上任何用户仍可绑全部 loopback 地址，此方案仅在部分平台有意义——不建议作为首发方案，写进"已考虑并否决"即可。

无论选哪条，ADR-0007 应补充一段"已知残余风险"。

**第 2 轮状态**：❌ 未处理。ADR-0007 原样保留，无 SECURITY.md，无 socket 方案评估记录。在远程写入协议（0017）和验证哲学（0011/0021）都已大幅加强之后，这成为剩余问题中**最实质**的一个。

## 问题 2：修改远程 shell 启动文件缺少安全规范（高）🟡 大幅改善

**相关文档**：[ADR-0002](../adr/0002-separate-the-tunnel-core-from-tool-adapters.md)、[ADR-0015](../adr/0015-hide-system-ssh-behind-a-deep-openssh-module.md)、[ADR-0017](../adr/0017-use-remote-compare-and-swap-for-managed-state.md)

**现状（第 1 轮）**：Codex 适配器"使用产品自有的远程环境文件 + 在受支持的 Bash/Zsh 启动文件中插入带标记的 loading block"。当时只描述了"插什么"，没有描述"怎么插、怎么验证可以插"：无 symlink/属主校验、无 shell 语法破坏防护、无值转义规则、无降级路径。

**风险（第 1 轮）**：这是整个产品中唯一向远程机器写入可执行内容（shell 代码）的操作，安全等级应高于本地 SSH 配置编辑。写入不当可导致：symlink 攻击写穿到任意路径；插入 block 与用户 `set -e`/`set -u` 交互破坏登录 shell；环境值含单引号/反引号/`$()` 导致远程任意代码执行；不支持的 shell 上行为未定义。

**第 2 轮状态**：🟡 大幅改善，主体已覆盖：

- **0017** 的远程 CAS 协议覆盖了 symlink 校验、权限受限临时文件、保 mode、同文件系统 rename、后置证据——文件层写入安全解决；
- **0015** 规定远程操作白名单 + 固定 POSIX sh 脚本 + **payload 走 stdin 而非命令文本** + 参数严格编码 + 未知操作 fail closed——命令注入面解决；
- **0002（修订）**把远程环境文件与启动文件 block 收归共享 Remote Environment 模块，适配器不再持有写文件能力；
- **0020** 的 Ownership Descriptor（文本区域用成对标记）为定位与回滚提供依据。

**剩余缺口**：

1. **插入 block 的自防御性仍未规定**：用户启动文件中的 `set -e`、`set -u`、`inherit_errexit`、非交互分支下早退 `return` 等场景，插入的 block 若引用未定义变量或返回非零，仍可能破坏用户登录 shell。建议规定 block 内部所有变量引用带默认值、整体不中断外层执行。
2. **环境文件的值转义格式**未钉死：payload 走 stdin 解决了传输层注入，但环境文件内容本身（`export KEY=...`）的 shell 转义规则（建议单引号 + `'\''` 转义、拒绝换行）仍无 ADR 明文。
3. 降级路径（fish/tcsh 等不受支持 shell 的行为）仍只有"受支持的 Bash/Zsh"一句，未规定遇到其他 shell 是 Configured-Unverified 还是明确失败。

## 问题 3：Transaction Record 缺少权限、并发与敏感度说明（中高）🟡 部分解决

**相关文档**：[ADR-0003](../adr/0003-treat-configuration-as-a-verified-transaction.md)、[ADR-0012](../adr/0012-serialize-v0-1-mutations-globally.md)、[ADR-0013](../adr/0013-record-transactions-with-an-append-only-journal.md)

**现状（第 1 轮）**：事务记录为本地脱敏文件，存于平台 per-user 应用数据目录，保留最近 10 条。未规定文件权限、并发、脱敏字段清单。

**风险（第 1 轮）**：权限未定则记录中的 SSH 主机别名、路径、端口可能被同机其他账户或备份读取；并发读写使"读记录 → 比对 → 写入"非原子，drift 检测失效；"脱敏"与"回滚需要真实先验值"存在张力但无分界。

**第 2 轮状态**：🟡 部分解决：

- **并发**：由 0012 全局互斥锁完整解决（跨进程序列化所有变更操作，只读检查可并发）；
- **完整性**：由 0013 append-only journal（framed record、序列号、完整性校验、fsync 语义、损坏尾条隔离）大幅加强；
- **敏感度分类**：由 0018 的四级分类（public / user-identifying / sensitive / secret）建立了框架。

**剩余缺口**：

1. **文件权限数值仍未规定**：journal、Transaction Record、当前状态摘要文件创建时的权限（`0600` / Windows ACL 等价物）没有任何 ADR 钉死。0016 把权限行为推给内部 seam 的契约测试，但"应该测什么权限值"本身是设计决策。0017 只覆盖了**远程**文件的 mode 保留，本地文件无人认领。
2. 脱敏与回滚真实数据面的分界仍不清晰——已升级为新问题 N3（见 [002-reliability.md](002-reliability.md)）。

## 问题 4：SSH managed include 文件缺少路径、权限与原子写入规范（高）🟡 部分解决

**相关文档**：[ADR-0004](../adr/0004-own-ssh-forwarding-through-a-managed-include.md)、[ADR-0017](../adr/0017-use-remote-compare-and-swap-for-managed-state.md)

**现状（第 1 轮）**：反向转发指令写入产品所有的 Include 文件，主配置只加一条最小 Include 指令。未规定文件物理属性：路径、权限、原子写入、symlink 校验、Include 指令的移除匹配方式。

**风险（第 1 轮）**：`~/.ssh/config` 是本产品修改的最高价值目标文件。组/其他用户可写的 include 等于任何人都能改写 SSH 行为（如插入 `ProxyCommand` 执行任意命令）；truncate + 写入中途崩溃永久损坏主配置；symlink 覆盖任意文件；Include 行移除时匹配失败或误删用户手工整理过的行。

**第 2 轮状态**：🟡 部分解决：

- **0004（修订）**补充了重要语义细节：Include 指令固定插入位置（顶层全局指令之后、第一个 Host/Match 之前，绝不落进既有上下文）；插入与移除后都检查目标与非目标生效配置；
- **0017** 的 CAS 协议（symlink 校验 + 临时文件 + rename + 后置证据）为**远程**文件提供了模板，但**未声明是否同样约束本地 SSH 配置写入**；
- **0012** 全局锁解决了本地多实例并发写。

**剩余缺口**：

1. 本地 `~/.ssh/config` 与 managed include 的**写入是否采用与 0017 相同的原子 CAS 语义**（临时文件 → lstat 校验 → rename）——建议直接声明"本地写入与远程写入遵循同一 CAS 协议"，一行 ADR 即可闭环；
2. include 文件与 `~/.ssh` 的权限数值（`0600`/`0700`）仍未规定（与问题 3 剩余缺口同源，见"本地持久化安全规范"建议）；
3. Include 指令移除时的精确匹配策略（按插入时字节快照匹配、失配报 drift）仍未写明——0004 只说检查生效配置，没说怎么安全删那一行。

## 问题 5：用户提供的 SSH alias 未定义校验规则（中）❌ 未处理

**相关文档**：[ADR-0004](../adr/0004-own-ssh-forwarding-through-a-managed-include.md)（"permits a user-supplied alias"）

**现状**：目标选择列出显式、非模式的主机名，但允许用户手工输入一个 alias，至今没有定义合法字符集和格式。

**风险**：

1. 用户输入 `*`、`*.example.com`、`!*prod` 等模式字符串，被当作字面 Host 名写进 managed include 后，转发配置会匹配到远超预期的连接——最坏情况：用户任何一次 SSH（包括到生产机）都带上反向转发端口，把本地代理暴露到生产机上（与问题 1 叠加）；
2. 含空格、引号、换行的输入会破坏 include 语法或注入额外 ssh_config 指令（如夹带 `\n  ProxyCommand ...`，即配置注入）；
3. alias 与用户已有 wildcard Host 块叠加时，OpenSSH"首现即用"规则使 include 的加载顺序影响语义——0004 修订版固定了插入位置，但该顺序对 wildcard 叠加的具体影响仍未讨论。

**理由**：这是产品中唯一一处**用户自由文本进入 SSH 配置文件**的通道，属于经典注入面。ADR-0004 防住了"解析侧"（`ssh -G` 验证），0017 防住了"写入侧竞态"，但没人防"写进去的内容本身是危险值"。

**建议**：定义 alias 白名单字符集（建议 `[A-Za-z0-9._-]+`，长度上限），拒绝任何含 `*?!` 空白、引号、`:`、`/`、换行的输入；写入后用 `ssh -G <alias>` 复核生效配置确实指向预期主机。成本极低（一条 ADR 补充），建议尽早闭环。

**第 2 轮状态**：❌ 未处理。

## 问题 6：Recovery-Required 状态缺少用户侧逃生通道（中）❌ 未处理

**相关文档**：[ADR-0003](../adr/0003-treat-configuration-as-a-verified-transaction.md)、[ADR-0013](../adr/0013-record-transactions-with-an-append-only-journal.md)

**现状（第 1 轮）**：被打断的事务限时回滚，否则记为 Recovery-Required；后续命令先诊断该记录再允许其他变更；没有 force flag。用户在自动恢复失败后的手动路径没有任何文档。

**风险（第 1 轮）**：安全机制"没有逃生门"只有在"门内一定能解决"时才成立。ADR-0003 的立场（宁可停也不盲动）是对的，但它把终局责任推给了用户，却没给用户手册。用户的退路会退化为：永久弃用工具（留一堆 managed 残留），或自己瞎猜删文件（可能删掉自己的配置）。

**第 2 轮状态**：❌ 未处理（恢复**语义**更严谨了：0013 明确 v0.1 恢复"仅当全部 mutation 与后置条件被证明才允许重新验证，否则准备 Compensating Rollback，从不续跑未完成的 apply 序列"——这加强了自动恢复的确定性，但用户侧手动恢复指南仍然不存在，且 0013 的严格化反而抬高了对手册的需求：自动恢复能做的事越少，用户需要自己动手的场景就越多）。

**建议**：补一份 `docs/runbook/manual-recovery.md`，列出产品可能触碰的全部位置清单（本地：SSH 主配置 Include 行、managed include、journal/记录目录、Plan Token 存储；远程：环境文件、启动文件中的标记块），每项给出识别方法与安全移除方法；`doctor` 检测到 Recovery-Required 时直接输出对应清单路径。

## N1（新增，第 2 轮）：Plan Token 的本地威胁模型未声明（中）

**相关文档**：[ADR-0010](../adr/0010-use-an-inspect-prepare-execute-workflow-interface.md)

**现状**：Plan Token 是"本地持久化、15 分钟有效、只能消费一次、绑定 schema/工作流版本、Change Plan 摘要、目标与端口选择、观察状态摘要与风险确认"的不透明引用。

**风险**：本地持久化 + 可消费意味着——能读应用数据目录的任何本地进程可以在有效期内抢先消费 token，触发一次已被批准的变更。product 本身无法抵御本地恶意进程（它自己就要改 SSH 配置），这个边界可以接受；但 ADR-0010 没有显式声明它。"opaque + 一次性 + 短时效"的组合容易被实现者或未来贡献者误读为一种安全凭证（如防伪造令牌），从而在实现时省略本应有的持久化权限控制。

**理由**：token 的真实安全属性是**防误用与防跨进程误消费**（配合 0012 的全局锁），不是防本地恶意读者。威胁模型声明缺位的典型后果是有人日后提议"把 token 加密存储以防偷取"，浪费工程量在错误方向。

**建议**：在 0010（或 SECURITY.md）补一句声明："Plan Token 假设本地进程环境可信；它约束的是批准的原子性与新鲜度，不防御能读取本地应用数据的恶意进程。"同时写明过期/消费后的 token 记录是立即删除还是保留为证据。
