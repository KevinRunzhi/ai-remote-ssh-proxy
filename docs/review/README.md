## 第 2 轮总体评价

新增 ADR 0010–0021 不是对第 1 轮反馈的机械回应，而是系统性补齐了模块边界（0010 inspect/prepare/execute、0015 OpenSSH 深模块、0016 平台 seam）、持久化语义（0013 append-only journal、0019 独立版本化）和验证哲学（0011 区分配置验证与活动端点验证、0021 把 `ExitOnForwardFailure` 限定在验证连接）。其中：

- **0011/0021 超出了第 1 轮建议的深度**：不仅处理了端口探测 TOCTOU（问题 7），还发现并正确解决了"验证连接自证"问题（验证转发的连接自己创建了被验证的端点）和"持久配置设 `ExitOnForwardFailure` 会拒杀第二个普通 SSH/VS Code 会话"这两个第 1 轮评审未识别的隐患；
- **0015 对 `ssh -G` 执行用户 `Match exec` 命令的显式披露与用户确认**，是很多成熟项目都会漏掉的安全细节；
- **0012 的全局互斥锁**以"共享 include、本地状态、多别名同目标"论证了为何不能按 SSH Target 分锁，比第 1 轮建议更完整。

## 当前最大的结构性缺口

安全面没有集中载体。以下内容分散或缺失，应全部归入一份 `SECURITY.md` / 威胁模型：

1. 远程同主机其他用户可访问 loopback 转发端口（问题 1，未处理）；
2. Plan Token 的本地威胁模型（N1，新增）；
3. 本地文件（SSH include、journal、Transaction Record）的创建权限数值（问题 3/4 剩余部分）;
4. 各"范围外"边界的集中声明（认证代理、GatewayPorts、非 OpenSSH、远程 Windows、多用户共享主机）。

## 建议处理顺序（第 2 轮后）

1. `SECURITY.md`：集中威胁模型 + 披露流程，一并解决问题 1 的声明义务、N1、问题 13；
2. journal 轮转与 Recovery-Required 证据的关系（N2）——这是正确性问题，应在实现 journal 前定案；
3. alias 校验规则（问题 5）——一行 ADR 补充即可，成本最低；
4. 脱敏与回滚数据面的分界（N3）+ 本地文件权限数值（问题 3/4 剩余）——可合并为一份"本地持久化安全规范"；
5. 手动恢复手册（问题 6）、README/模板残留（问题 12/14）。
