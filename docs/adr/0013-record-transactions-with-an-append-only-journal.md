# Record transactions with an append-only journal

Each Configuration Transaction begins with an immutable header and records ordered stage and operation evidence in an append-only Transaction Journal; a disposable current-state summary may be rebuilt from that journal. A single mutable status object cannot distinguish a completed mutation from a status write lost during a crash, while event-sourcing the whole product would add unnecessary projection and migration complexity.

## Consequences

The durable stages are `recorded`, `applying`, `verifying`, `committed`, `rolling_back`, `rolled_back`, and `recovery_required`. Cancellation is recorded as a `cancellation_requested` event rather than a transaction stage or terminal state. Each mutation records its precondition digest, apply start and completion, postcondition evidence, and compensation start and completion. Journal entries are append-only framed records with a schema, monotonic sequence, length, and integrity check. The header and every event bracketing an external side effect are flushed before execution can advance. A partial or corrupt trailing entry is ignored or quarantined, the current summary is rebuildable, and a host unable to provide the required durable write behavior is blocked from mutation.

Automatic Compensating Rollback remains part of the failing transaction. A later user-requested Rollback, Repair, or Unconfiguration is a new Configuration Transaction that references its source rather than rewriting an earlier committed record. For Recovery-Required in v0.1, the journal may authorize renewed Verification only when all mutations and postconditions are proven; otherwise it may prepare Compensating Rollback. It never resumes an incomplete apply sequence, and Configuration Drift stops automatic recovery.

While any Recovery-Required Transaction remains unresolved, v0.1 permits inspection and preparation of its dedicated recovery or rollback plan but blocks execution of every unrelated mutation. This deliberately coarse safety gate matches the global mutation lock and protects shared resources until later resource-level locking can narrow the scope safely.

The Journal is private operational state stored with restrictive per-user permissions. It may retain exact resource paths and other sensitive but non-secret identifiers required to recover after a restart. It never stores credentials, tokens, authenticated proxy URLs, or other values classified as secret; a Change Plan requiring secret compensation data is rejected before mutation.

The ordinary retention limit keeps the most recent ten settled Configuration Transactions per Tunnel Profile. An unresolved Recovery-Required Transaction, its Transaction Record, and every record required to interpret or resolve it are pinned and never participate in ordinary rotation. Recovery Reconciliation appends a `resolved_by` link only after a Repair or Rollback Transaction proves that every affected resource has reached a coherent known state; the linked records become eligible for normal rotation afterward. No acknowledgement or force option may discard uncertainty without that evidence.
